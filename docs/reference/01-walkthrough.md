# 第 6 章：参考实现（订单履约问答）

这不是一个可运行产品。它用知识库本体教程里的“订单与履约”例子，把前面各章串成一条只读问答加受控查询。目的是检查章节之间是否还缺产物。

## 6.1 需求

值班人员在客户询问“这张国际订单为什么还没发货”时，要在 10 分钟内给出有出处的状态说明。答错运费或承诺赔付的成本高。本次非目标：自动改订单、自动赔付、自动给客户发消息。

自主性：订单状态是受控只读；制度解释是带引用的问答；任何写操作不做。

验收例子：

- 正例：给定订单号，回答状态、发往城市，并引用业务记录时间和制度条款位置。
- 反例：资料没有赔付规则时，不生成赔付承诺。
- 越权：其他租户的订单号不能被检索到。

## 6.2 Clarity 和 Scene

术语：国际订单是订单的一种；“发往”指向城市；城市属于区域。这些是 L1 术语。字段形状用现有订单 API 的 JSON，属于 L2，不新建 OWL。

工作流状态仍由订单系统维护：已支付、待发货、已发货、异常。Agent 只在“人正在处理客户询问”这个活动里被调用。它不推进发货状态。

数据：订单事实从订单 API 读，身份沿用客服的权限。制度 PDF 来自已发布知识库。两者的时间都要出现在回答里。

## 6.3 设计决定

ADR 决定：

- 采用固定 RAG 管道，不用 Agent 自行决定要不要查库。要查的就是订单 API 和制度索引。
- 订单 API 是只读工具，参数只有订单号，网关检查客服是否能看这张订单。
- 制度索引按租户过滤，Embedding 模型和索引版本写在配置里。
- 回答 Schema：`status`、`city`、`policy_quotes`、`unknowns`。`unknowns` 非空时，用户可见文本不得出现赔付承诺。
- 暂不引入图数据库。若以后稳定出现“沿区域找履约中心”的多跳问题，再评估 L3。

被放弃的方案：让一个多 Agent 系统先讨论再回答。当前步骤是固定的，多 Agent 只增加失败面。

## 6.4 运行时

1. 客服输入订单号和问题。
2. 网关用客服身份调用订单只读 API。无权限则停止。
3. 用问题和订单状态检索本租户的制度切片，关键词加向量，再重排。
4. 模型只能根据 API 结果和切片填写 Schema。
5. 校验器检查引用标识属于本次检索结果。
6. 界面展示状态、引用和未知项。客服自己决定怎么回复客户。

知识版本、模型版本和 Prompt 版本写进 Trace。

## 6.5 发布和一次事故

发布矩阵包含：客服界面构建号、订单工具 Schema、Prompt 哈希、制度知识版本、索引构建号、Embedding 模型名。评测含上面的正例、反例和越权。

事故例子：模型在 `unknowns` 已标明没有赔付条款时，仍生成了赔付句子。处理顺序：

1. 打开只读降级，回答只展示 API 字段和原文切片，不再生成散文。
2. 用 Trace 确认是哪一版 Prompt。
3. 回滚 Prompt，保留索引。
4. 把这条样本加入评测，断言 `unknowns` 非空时输出不含赔付句。
5. 复盘是否要把“赔付”相关句子做成 Guardrail。那是 L4 的候选，不在本次事故里临时上 OWL。

## 6.6 这条例子故意没做的事

- 没有微调。制度更新比权重频繁。
- 没有本体推理。子类关系还没用能力问题证明需要推理器。
- 没有向量库里的事务。订单状态只来自 API。
