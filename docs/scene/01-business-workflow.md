# 3.1 Business Workflow

Scene 的这一半描述人怎么工作，以及 Agent 被允许进入哪一步。它来自 Clarity 的草稿，在设计阶段被 Architect 收成状态和工具权限。

## 3.1.1 方法论

先把业务流程写成状态，再决定哪一个状态可以由模型推进。

每个状态写清：

| 项 | 内容 |
| --- | --- |
| 角色 | 谁对这个状态的结果负责 |
| 进入条件 | 什么事件把它打开 |
| Agent 可以做的事 | 只读、起草、调用哪类工具 |
| 人必须做的事 | 审批、确认、补材料 |
| 成功后的状态 | 可观察的业务结果 |
| 失败后的状态 | 退回、补偿、升级 |
| 副作用 | 会改哪些外部对象，幂等键是什么 |

固定顺序、每步输入输出都稳定的流程，用持久化工作流来保存状态和人工任务。模型只在其中某一个步骤里做分类、摘要或起草。开放式的多步判断，才让 Agent 选择下一步，并且每一步仍要落在允许的工具集合里。

不要用 Agent 循环代替工作流引擎的原因：

- 循环没有耐久状态时，进程重启会丢掉做到哪一步。
- 模型可能重复执行已经成功的写操作。
- 审计需要的是状态迁移，不是一段事后生成的叙述。

不要用工作流引擎硬编码开放判断的原因：

- 分支来自非结构化文本，规则表会迅速过期。
- 这种步骤的验收方式是评测集，不是一条布尔表达式。

知识库里的订单与履约练习可以当成示例场景：下单、支付确认、发货、异常补偿是工作流状态；“这张订单是否违反某条制度”如果要引用制度原文，是某个状态里的检索步骤，不是另一个不受控的 Agent。

## 3.1.2 AI Coding 技巧和注意点

技巧：

- 用真实工单和操作记录让模型列出候选步骤，人删掉只发生过一次的例外。
- 每个写步骤同时生成成功条件和补偿说明。补偿写不出来的步骤，不能自动执行。
- 把审批画成工作流里的人工任务，而不是 Prompt 里的“请确认”。

注意点：

- 模型会把审批画成自己调用自己。审批人必须是身份系统里的人。
- 从录屏提取的步骤常含有个人账号和客户数据，进入仓库前要脱敏。
- 业务流程文档和运行中的工作流定义会分叉。运行中的定义以版本库里的工作流源码为准，叙述文档由它生成或在评审时对齐。

## 3.1.3 工具如何接入

工作流引擎负责任务状态、定时、重试和人工任务。Agent 运行时只作为某个活动的实现。活动失败时，引擎按已声明的策略重试或升级，不由模型自行决定无限重试。

| 对比 | 工作流引擎中的活动 | Agent 循环 |
| --- | --- | --- |
| 下一步由谁决定 | 流程定义 | 模型在允许的工具里选择 |
| 状态 | 引擎持久化 | 需要额外的检查点，否则重启即丢失 |
| 适合 | 已知步骤、审批、补偿 | 开放判断、起草、检索式问答 |
| 审计 | 状态迁移天然留下 | 必须额外记录每次工具和决定 |

这一轮打开过说明的引擎是 Temporal 和 Camunda 8，对照见 [tools.md](../reference/tools.md) 第 14 节。选择时看人工任务、幂等、可见的历史，以及失败后能否从步骤恢复。

## 3.1.4 和本体姿态的关系

- Contract：每个活动的输入输出使用同一套字段名。
- Guardrail：离开活动之前检查输出形状和业务规则。
- Index：只在需要沿订单、客户、区域等多跳关系取证时使用。
- Memory：流程里新发现的别名进入候选区，不直接改正式术语。

## 3.1.5 退出条件

- 每个写动作有成功条件、幂等和补偿或升级。
- Agent 介入点是少数状态，不是整条流程。
- 审批人来自身份系统。
- 工作流定义有版本，和 Scene 文档一致。
