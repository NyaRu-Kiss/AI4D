# 3.2 Data Center

Scene 的另一半描述数据放在哪里、谁拥有、Agent 以什么身份读取。这里的“数据中心”是逻辑分层，不是机房。

## 3.2.1 分层

| 层 | 保存什么 | 不负责什么 |
| --- | --- | --- |
| 业务库 | 订单、账户等事务 | 相似度检索、长文档解析 |
| 文档与对象存储 | 制度、合同、附件原文 | 语义查询 |
| 分析平台 | 聚合后的历史和指标 | 在线事务和逐条授权问答 |
| 知识服务 | 解析后的切片、元数据和引用 | 替代原文的法律文本 |
| 向量库 | 切片的向量和过滤字段 | 事实约束和业务事务 |
| 图存储 | 实体和关系，或 RDF | 替代向量做模糊措辞召回 |
| 模型服务 | 推理 | 数据所有权和长期记忆 |
| 日志与审计 | Trace、动作、审批 | 作为第二套业务库被人直接改 |

一层只通过它公开的接口被上一层使用。Agent 不持有业务库的管理员账号。

## 3.2.2 方法论

1. 每个数据源有所有者、分类、保留期和删除方式。没有所有者的数据不进入知识库。
2. 权限在检索之前过滤。把文档取进模型再要求它“不要说出其他租户的内容”，挡不住提示注入。
3. 原文、切片、向量、日志是四份副本。删除请求要能到达这四份，或明确哪一份因审计法规必须保留以及保留多久。
4. 知识更新和业务事务分开。订单状态以业务库为准。制度文本以已发布的知识版本为准。回答里引用两者时，要标明各自的时间。
5. 生产和开发隔离。Coding Agent 使用脱敏样本或合成数据。生产全量导出不能成为开发上下文。

租户隔离至少到知识库、向量集合和日志查询。只在应用层用 `if tenant` 拼接提示，而集合里混着所有租户的向量，过滤条件一旦漏掉就会串数据。

## 3.2.3 AI Coding 技巧和注意点

技巧：

- 让模型根据样本生成解析和校验脚本，人用一批真实文件的黄金样本验收，包括扫描件、表格和空文件。
- 管道输出写血缘：原文标识、版本、切片标识、Embedding 模型、写入时间。
- 为删除和过期做一条自动检查：抽到的切片必须能回到仍有效的原文。

注意点：

- 生成的管道经常把失败文件悄悄跳过。跳过必须计数并告警，否则知识库会静默缺章。
- 模型建议“先把所有库同步到一个向量库”时，先问数据分类是否允许复制。
- 分析平台里的宽表可能含有个人数据。把它接进 RAG 之前，要有和业务库相同的目的限制。

## 3.2.4 工具如何接入

数据平台工具很多，本章只固定接入原则：

- 业务事务留在现有 OLTP。AI 应用通过 API 读，不复制一份可写的影子库给 Agent。
- 原文进对象存储或文档系统，知识服务保存切片和元数据。
- 向量库和图存储是索引，重建它们不应丢失原文和业务事务。
- 密钥和策略由平台统一发放，Coding Agent 只看到开发环境的短期凭证。

产品名称和优缺点在工具附录中按检索结果填写。选型时用第 1 章的五条样本，外加一条删除样本：原文删除后，检索、日志和引用都不再返回它，或按保留策略只留审计不可读正文。

## 3.2.5 退出条件

- 数据源清单含所有者、分类和保留期。
- Agent 的数据库身份不能越过工具网关。
- 删除或过期能到达原文、切片、向量和日志策略。
- 开发环境没有生产全量数据。
