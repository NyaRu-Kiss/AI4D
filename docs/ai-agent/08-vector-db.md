# 4.8 Vector Database

向量数据库保存向量和用于过滤的元数据，并按选定的距离返回近邻。它是索引，不是事实来源，也不是业务事务库。

## 4.8.1 和其他存储的分工

| 存储 | 回答的问题 | 丢失后如何恢复 |
| --- | --- | --- |
| 原文和业务库 | 什么是真的、谁有权改 | 按数据库和对象存储的备份 |
| 文档索引（关键词） | 哪些词和条款号出现过 | 由原文重建 |
| 向量库 | 哪些切片在向量空间里接近查询 | 由原文和 Embedding 模型重建 |
| 图数据库 | 实体沿哪些关系相连 | 由事实和本体重建 |

向量库损坏时，业务订单仍然在事务库里。恢复的是索引构建作业，不是从向量反推原文。因此向量库的备份策略可以和事务库不同，但重建时间和 Embedding 费用要写进恢复目标。

## 4.8.2 方法论

1. 写入时带上租户、权限标签、知识版本、原文标识、切片标识、模型名和维度。
2. 查询时先施加租户和权限条件，再做近邻搜索。如果产品做不到在过滤条件下搜索，就不要把它用于多租户知识库，或者只在已经按租户物理分开的集合上搜索。
3. 混合检索需要关键词索引。只有向量的库，条款号和错误码会不稳。关键词可以在同一个产品里，也可以在旁边的搜索引擎里，由应用合并。
4. 集合按知识版本或按租户划分，以删除和重建便宜的那种为准。变更 Embedding 模型时新建集合，评测通过后再切换读流量。
5. 容量看向量维度、条数、过滤字段和查询并发，不看“能不能存百万级”的宣传。用生产形状的数据做一次装载和一次重建计时。

多租户优先使用产品文档里写明的机制：独立集合、payload 过滤或分区。只在应用里记住“应该加过滤”而索引里没有这个字段，下一次查询就会串租户。

## 4.8.3 AI Coding 技巧和注意点

技巧：

- 为向量访问写一个小接口：`upsert`、`delete_by_document`、`search`。测试用本地或容器里的同一产品，避免测试打到托管生产实例。
- 删除测试：写入两租户，删除其中一个文档，断言另一个租户的结果不变，且被删文档不再出现。
- 把索引构建做成可重复的作业，输入是知识版本，输出是集合名。

注意点：

- 生成的建表脚本可能没建过滤字段的索引，过滤会在大数据量时退化为全扫描或被客户端忽略。
- 近似搜索的参数会影响召回。改参数等于改行为，要重跑检索评测。
- 把向量库当成可以随意更新单行的事务库，会和重建作业互相覆盖。写入路径只来自索引作业。

## 4.8.4 工具如何接入

应用只依赖自己的接口。适配器负责某产品的客户端、过滤语法和混合查询。切换产品时重写适配器，不改 RAG 评测的期望。

对照维度固定为：部署形态（库内扩展、独立服务、托管）、过滤、混合检索、多租户、备份或重建、许可证、优点和局限。行只收录检索笔记打开过文档的产品，写入 `docs/reference/tools.md`。

## 4.8.5 退出条件

- 过滤字段和模型版本写在集合元数据里。
- 删除和越权测试通过。
- 重建时间、费用和切换步骤写进运行手册。
