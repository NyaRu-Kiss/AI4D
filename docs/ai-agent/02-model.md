# 4.2 Model

模型是执行面里的一个可替换组件。它负责不稳定的语言判断和草稿。它不负责权限、事务和事实的最终确认。

## 4.2.1 方法论

按任务选模型，不按参数规模选。路由维度是：输出质量（用评测集）、延迟、费用、数据能否出域、工具调用是否稳定、上下文是否装得下该任务的证据。

| 任务 | 通常更合适的模型特征 | 理由 |
| --- | --- | --- |
| 分类、抽取、路由 | 小一些、延迟低、结构化输出稳定 | 步骤频繁，错误可以用 Schema 挡住 |
| 起草和改写 | 指令遵循好 | 人会再改 |
| 多步工具调用 | 工具调用稳定、失败可解析 | 格式错误会卡死编排 |
| 高风险判断的草稿 | 质量优先，并且仍然只输出建议 | 错误成本高，速度不是第一约束 |

推理模型会花更多步骤处理困难问题，也更慢、更贵。只把它用在评测证明“直接回答不够”的步骤上，不要让每一次检索都走推理模型。

选择顺序：

1. 用现有模型和检索、Schema 把任务评测跑起来。
2. 换一个更合适的通用模型，比较同一评测集。
3. 仍然失败，而且失败来自稳定的领域格式或大量重复任务，再评估微调或专用小模型。
4. 微调不替代检索。制度会变，微调权重不会在文档发布的同一天更新。

Prompt 是版本化资产。它写任务、输出形状和拒答条件。它不写密钥，不写“你可以访问所有数据库”。

结构化输出用 Schema 校验。校验失败时有限次重试，把校验错误返回给模型。超过次数就停止并把原文交给人。不要为了解析成功而放宽 Schema。

上下文预算先分配给：系统指令、用户任务、必须遵守的策略摘要、检索证据、工具结果。证据不够就拒答或再检索，而不是换一个更长的窗口把整个知识库装进去。更长的窗口仍然会忽略中段，见 RAG 一章。

生产配置使用不可变的模型版本。别名只允许出现在开发环境，并且评测报告要记下别名在当天解析成的版本。

## 4.2.2 本地服务和外部 API

数据不能出域时，模型放在受控环境里，由团队自己的服务加载权重。可以出域时，使用供应商 API，并在合同或文档里确认输入是否用于训练。两条路都经过同一个模型客户端接口：输入消息、工具定义、Schema、超时；输出文本或工具调用、用量、模型版本。

路由网关可以按任务把请求发到不同模型，并在主模型不可用时降级。降级模型必须在评测里有记录。静默降级到未评测模型，视为一次发布。

本地服务要单独看：GPU 容量、队列、模型加载时间、权重来源和许可证、以及升级权重时如何切换版本。这些是 OPS 的容量问题，不只是开发库的选择。

## 4.2.3 AI Coding 技巧和注意点

技巧：

- 把路由写成配置：任务名到模型版本。配置走评审。
- 为每个任务保存失败样本。换模型时只比较这些样本和原有评测集。
- 记录每次调用的用量。没有用量就无法在运营里设置预算告警。

注意点：

- 模型会虚构工具参数里的标识符。标识符必须来自工具结果或用户输入，并用 Schema 和存在性检查验证。
- 把思维链要求进生产 Prompt，可能增加延迟和费用，还可能在日志里留下不希望展示给用户的内容。需要的是可检查的结构化结果，不是一段看起来像推理的文字。
- 微调数据如果含有个人数据或客户文档，它的保留和删除要求与知识库相同。

## 4.2.4 工具如何接入

| 组件 | 接入点 | 要求 |
| --- | --- | --- |
| 供应商 API | 模型客户端的一种适配器 | 固定版本、超时、用量 |
| 本地推理服务 | 另一种适配器 | 健康检查、版本和许可证记录 |
| 路由网关 | 客户端内部或独立服务 | 路由变更可审计，降级模型已评测 |
| 结构化输出库 | 调用之后的校验 | 失败次数有上限 |

网关、本地运行时和 Agent 框架的对照见 [tools.md](../reference/tools.md) 第 10 节和第 11 节。没有打开文档的产品不在表里。

## 4.2.5 退出条件

- 每个任务绑定的模型版本写在配置里。
- 评测集能比较至少两个候选模型或同一模型的两个版本。
- 数据出域决定和训练使用决定已记录。
- 结构化输出失败有上限和人工路径。
