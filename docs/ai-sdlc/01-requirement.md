# 2.1 Requirement

负责人是 Product Owner。这一阶段决定“做什么”和“怎样算做成”。模型可以加快起草，不能代替范围签字。

## 2.1.1 这一阶段的产出

一份能进入 Clarity 的需求包，至少包括：

| 项 | 写什么 | 缺失时会发生什么 |
| --- | --- | --- |
| 目标用户和触发 | 谁在什么事件下碰到问题 | 后面的 Scene 没有入口 |
| 现状 | 今天人怎么做，耗在哪 | 模型会发明一条不存在的流程 |
| 期望结果 | 用户拿到什么 | 团队开始堆功能 |
| 错误成本 | 答错、做错、漏做分别伤到谁 | 自主性等级无从定 |
| 数据来源 | 事实来自哪套系统或文档，谁是所有者 | 检索会接到无权使用的库 |
| 允许的动作 | 只读、建议，还是可以写哪些对象 | 工具网关无法做最小权限 |
| 验收 | 哪些例子必须通过，哪些必须拒绝 | 评测集是空的 |
| 非目标 | 这次明确不做什么 | 范围在开发期膨胀 |

成功指标尽量写成可计数的结果：一次任务在时限内完成、人工修改率、错误工单数、单次成本上限。无法计数的感受，保留为观察项，不作为发布门禁。

## 2.1.2 方法论

1. 先写问题，再写方案。方案句（“做一个 Agent”“上 RAG”）退回到问题句（“值班人员要在 10 分钟内找到有出处的处置步骤”）。
2. 把验收例子和需求写在一起。每条需求至少有一个正例、一个反例。反例包括无依据、过期依据和越权。
3. 错误成本和自主性连在一起定级。高错误成本默认停在“建议”。
4. 数据和合规是需求的一部分。数据能不能出域、能不能用于训练、要保留多久，写进需求包，不留到上线前。
5. 需求文本进版本库，Issue 或工单链接到这条文本和后来的评测用例。聊天记录不是需求源。

规格驱动的做法把上述内容收成一份规格：背景、目标、非目标、场景、验收、边界。实现任务从规格拆出去。规格变了，评测用例一起变。

## 2.1.3 AI Coding 技巧和注意点

适合交给模型的草稿：

- 把访谈纪要整理成用户故事和待确认问题。
- 把一段现有操作说明改写成 Given-When-Then 草稿。
- 列出可能遗漏的非功能项：权限、审计、延迟、成本、离线、多语言。
- 对照旧需求，标出互相冲突的句子。

人必须重做的判断：

- 这条需求是否真实存在，优先级是否高于别的需求。
- 纪要里的数字、客户名、法规是否原句就有。模型补上的数字一律视为未证实。
- 验收是否可以被一个不会辩解的检查脚本或标注员判定。
- 非目标是否真的排除了范围。

常见失败：

| 失败 | 表现 | 纠正 |
| --- | --- | --- |
| 虚构用户和流程 | 故事完整，但公司里没有这个角色 | 每条故事回指一次真实样本：工单、录屏或日志 |
| 把方案写成需求 | “使用某向量库”出现在目标段 | 方案移到设计 ADR，需求只留问题和验收 |
| 验收无法判定 | “回答要专业、准确” | 改成一组问题和允许的依据文档 |
| 漏掉失败成本 | 只写了理想路径 | 补三列：答错、拒答、误操作 |
| 需求只活在对话里 | 下一轮模型看不到上次的非目标 | 规格文件入库，后续 Agent 只读这份文件 |

用 Coding Agent 改需求仓库时，限定它只能改 `docs/specs/` 下的草稿，不能改已经标记为 Accepted 的规格。Accepted 的修改走评审，和改接口一样。

## 2.1.4 工具如何接入

需求工具分三类。它们都要能把“已接受的规格”导出或同步到 Git，供后面的设计、评测和 Coding Agent 读取。

| 类别 | 在链路中的位置 | 接入要求 |
| --- | --- | --- |
| 协作Issue | 讨论、优先级、负责人 | 合并请求必须关联需求编号；关闭需求前检查验收例子是否入库 |
| 规格文件 | 版本、评审、差异 | Markdown 或等价文本放在仓库；状态用文件头或目录区分 Draft 和 Accepted |
| 规格辅助工具 | 从规格生成任务清单和检查项 | 生成物可以丢弃重建；规格原文才是源。工具升级不能改写已接受的句子 |

具体产品的对照见本章末尾的表。表内只收录本次检索打开过的项目。

## 2.1.5 同类工具对照

检索完成后填入。维度固定为：工具、它管需求的哪一段、怎么接到 Git 和评测、优点、局限、来源。

| 工具 | 管哪一段 | 接入 | 优点 | 局限 | 来源 |
| --- | --- | --- | --- | --- | --- |
| GitHub Spec Kit（`specify-cli`） | 规格驱动：原则、规格、计划、任务、实现和收敛；另有缺陷修复和想法评估扩展 | Python 3.11+ 与 `uv`。`specify init` 选择 Coding Agent 集成（文档示例为 GitHub Copilot）。后续命令在 Agent 对话里逐步执行，每步人工看过再继续。规格是 Markdown 产物 | MIT。把“先写清再实现”做成可重复过程，可换 Agent、可加组织预设和工作流 | 小改动也会多一轮规格；社区目录里的扩展页面写明未经审计，装之前要读源码。它不验证业务事实 | 2026-10-30 打开的仓库说明：[github/spec-kit](https://github.com/github/spec-kit) |

Issue 系统和文档仓库仍然是需求的归宿。Spec Kit 生成的规格要能被评审接受，并链到评测例子。本轮打开过页面的规格工具见 [tools.md](../reference/tools.md) 第 1 节。

## 2.1.6 退出条件

- Product Owner 接受了范围、非目标和验收例子。
- 自主性等级已标出。
- 数据所有者和能否出域已写明。
- 至少一条正例和一条必须拒绝的例子可以放进评测集草稿。
