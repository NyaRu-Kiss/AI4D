# 2.5 Deploy

部署阶段把已经通过审查的代码、模型、Prompt、知识、索引和策略一起放进可回滚的环境。只发布应用镜像，会让线上行为取决于没人记录的模型别名和索引。

## 2.5.1 方法论

一次发布有一张兼容矩阵，而不是一个版本号。

| 资产 | 发布时要固定的内容 | 回滚时要一起回到的状态 |
| --- | --- | --- |
| 应用代码 | 构建号和镜像摘要 | 上一构建 |
| 模型 | 供应商、模型 ID、不可变版本或快照 | 上一模型；若输出 Schema 不兼容则不能单独回滚 |
| Prompt | 模板哈希和评审记录 | 上一已接受模板 |
| 知识 | 文档版本和生效时间 | 上一已发布知识快照 |
| 索引 | Embedding 模型名、维度、索引构建号 | 与该知识快照一起构建的索引 |
| 策略 | 工具白名单和审批规则版本 | 上一策略；收紧策略可以单独提前发布 |

环境配置按环境分开，密钥不进镜像、不进 Prompt、不进 Agent 可读的仓库文件。

发布流水线的门禁至少包括：

1. 代码测试和安全扫描通过。
2. 离线评测达到该场景约定的门槛：任务成功、该拒答的拒答、越权样本被挡住。
3. 索引抽样能返回引用，且引用指向当前知识版本。
4. 策略快照和工具名单一致，没有多出来的写工具。

灰度看四类信号，而不只看 HTTP 错误率：任务是否完成、引用是否还在、有没有越权或未确认的写操作、单次成本是否超出预算。任何一类越过阈值，就停止扩大流量。

回滚演练要在上线前做过一次。演练包括“只回滚代码”和“代码、Prompt、索引一起回滚”两种，确认团队知道它们不是同一件事。

## 2.5.2 AI Coding 技巧和注意点

模型可以起草发布说明和兼容矩阵的空表。人核对矩阵里的版本是否真的存在于制品库。

注意点：

- 模型别名（“最新”“preview”）不能出现在生产配置里。别名会在无人变更应用的情况下改变行为。
- 评测失败后，不允许用改写门禁阈值的提交绕过。阈值变更单独评审，并说明为什么旧门槛不再代表风险。
- Agent 如果能改 CI 配置，它就能放宽自己的门禁。CI 定义的审查人和业务代码的审查人不能是同一个自动账号。
- 灰度环境如果连着生产知识库，测试流量会把实验性 Prompt 打到真实客户数据上。灰度使用数据子集和单独的审计标记。
- 特性开关可以关掉生成功能，退回只读检索或人工流程。开关本身要有所有者和过期时间。

## 2.5.3 工具如何接入

| 类别 | 接在哪 | 要求 |
| --- | --- | --- |
| CI | 合并和发布 | 测试、扫描、评测是合并的前置条件；机器人账号不能自行合并 |
| 制品库 | 镜像、索引包、Prompt 包 | 制品不可变，用摘要引用 |
| GitOps 或等价的声明式发布 | 环境状态 | 环境差异在 Git 里可审查；紧急变更事后补记录 |
| 特性开关 | 运行时降级 | 能在不重新训练和重建索引的情况下关闭写工具或生成 |

GitOps 和数据/模型版本工具的对照见 [tools.md](../reference/tools.md) 第 15 节。GitHub Actions、GitLab CI 这一轮没有打开产品页。发布门禁、模型标识和知识快照仍按本章执行。

## 2.5.4 退出条件

- 兼容矩阵已接受，生产配置没有浮动模型别名。
- 门禁在目标环境跑过，评测报告随发布单保存。
- 灰度指标和停滚条件已写明。
- 回滚步骤有人演练过，或明确记录为何本次不能演练以及补救时间。
