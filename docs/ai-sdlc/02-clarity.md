# 2.2 Clarity

Clarity 把已接受的需求变成可验证的问题，并形成 Scene 草稿。它没有单独的编制，通常由 Product Owner 主持，Architect 和将要实现的开发一起把歧义问完。

## 2.2.1 这一阶段要消除的歧义

| 歧义 | 要写成的明确句子 |
| --- | --- |
| 用户说的词和系统字段不是同一个东西 | 术语表：标准名、别名、对应字段、谁维护 |
| 不知道系统是在回答、建议还是执行 | 每个场景一个自主性等级 |
| 不知道答案从事实来，还是从模型推断来 | 标注：检索事实、规则计算、模型生成、人工决定 |
| 不知道失败时谁接手 | 拒答、转人工、重试、补偿各自的条件 |
| 不知道哪些输入算同一件事 | 触发事件、输入、输出、异常 |

澄清结束之前，不创建实现任务。实现任务里如果还写着“看情况”“尽量”“相关文档”，说明澄清没有完成。

## 2.2.2 方法论

1. 示例映射。拿三条真实样本，在桌上分成规则、例子、问题。规则写进规格，问题继续问人，例子进评测集。
2. Given-When-Then。Given 写权限和数据状态，When 写触发，Then 写可观察结果，包括不应发生的副作用。
3. 四类工作分开：
   - 事实：必须能指回来源。
   - 推理：必须能指出规则或本体公理，并和事实区分开。
   - 生成：起草文本或代码，人接受后才生效。
   - 执行：调用工具改变外部状态，走第 1 章的自主性等级。
4. 形成 Scene 草稿：角色、事件、状态、Agent 可以进入的状态、必须停下的状态、可读的数据类、可调用的工具类。细节在第 3 章展开，这里先把边界钉住。
5. 术语冲突升级到知识库的 L1。如果只是同一字段两种 JSON 写法，升级到 L2 的结构约束，不必上 OWL。

## 2.2.3 AI Coding 技巧和注意点

模型适合做的事：

- 阅读需求和样本，列出还没写清的问题。问题必须是人能用一句话回答的，而不是再生成一段方案。
- 把口语记录收成术语候选：标准名、出现过的别名、还不能确定的映射。
- 把一条规则改写成 Given-When-Then，并标出它发明的、原文没有的条件。
- 对照接口草稿和需求，指出两边用词不一致的字段。

注意点：

- 模型会把“可能”写成“必须”。澄清稿里，模型新增的约束用单独标记，评审时要么接受进规格，要么删掉。
- 不要让模型一次生成完整 Scene 并直接交给开发。Scene 里的停机条件和数据类，由对业务负责的人逐条确认。
- 澄清对话本身可能含有客户数据和密钥。给模型的上下文只用脱敏样本。
- 一个 Prompt 不要同时要求它“补全需求、设计架构、写出接口”。澄清阶段的 Prompt 只产出问题和候选句子。

和 Coding Agent 的衔接：澄清完成后，把已确认的术语表、验收例子和禁止事项写成仓库里的短文件，例如 `AGENTS.md` 里的任务边界或规格目录中的 `acceptance.md`。Agent 后续只被允许把这些文件当约束，不能把澄清聊天记录当规格。

## 2.2.4 工具如何接入

这一阶段的工具是文档和例子，不是运行时框架。

| 用途 | 接入方式 |
| --- | --- |
| 问题清单 | 跟需求放在同一份规格里，关闭问题才改状态 |
| 例子 | 表格或 YAML：输入、上下文、期望行为、是否必须拒绝。后来原样变成评测集 |
| 术语候选 | 先用表格。确认后再决定是否进入 SKOS 或本体，见第 4.5 节 |
| 会议记录 | 只作证据。决定写回规格，避免两处文案不一致 |

## 2.2.5 退出条件

- 每个目标场景都有自主性等级、输入、输出、拒答条件。
- 术语表里没有未决的同名异义，或未决项已明确延期。
- Scene 草稿能指出 Agent 进入和必须退出的状态。
- 正例、无依据反例、越权反例已经各有至少一条，并且人确认过期望行为。
