# 2.4 Development

前端、后端和 Agent 工程师在这一阶段把已接受的设计和规格变成可审查的变更。模型可以写草稿和测试，合并责任仍在代码所有者。

## 2.4.1 方法论

1. 任务从规格拆出，一次变更只解决一个问题，并带上可运行的检查命令。
2. 上下文只放任务需要的契约、相关目录和验收例子。整个仓库或生产数据无筛选地交给模型，会增加噪声，也会把密钥和客户数据送出域。
3. 生成代码走和人写代码相同的门禁：格式、静态分析、测试、依赖和许可证检查、人工审查。
4. 接口契约是实现的上位文档。模型如果要改接口，先改契约和规格，再改调用方。
5. 数据库迁移、权限、支付、删除和外部写操作，先提交计划和影响面，人接受之后才允许执行。
6. Prompt、工具 Schema、评测脚本和业务代码分开展示差异，避免一个巨大提交里混着四类变更。

DORA 在 2025 年《State of AI-assisted Software Development》的公开摘要里写明：生成式 AI 主要是放大器，会放大组织既有的优点和弱点；收益来自交付系统本身，而不是工具单独带来的。因此开发阶段先修评审、测试和任务切分，再增加 Coding Agent。来源：<https://dora.dev/research/2025/dora-report/>（2026-10-30 检索）。同一天打开的 [DORA AI 入口](https://dora.dev/ai/) 把《ROI of AI-assisted Software Development》标成最新报告，并单列 AI Capabilities Model。这两份正文没有打开，这里不摘录它们的结论。

## 2.4.2 前端

技巧：

- 给模型组件约束：使用仓库里已有的设计系统和状态管理，不引入第二套 UI 库，除非 ADR 允许。
- 每个界面同时写出空态、加载、错误、无权限。只生成理想路径的页面不算完成。
- 交互用可重复的端到端检查覆盖主路径，而不是只看截图。
- 文案和数据分开。模型生成的示例数据不能留在生产构建里。

注意点：

- 模型会按训练分布发明不存在的组件 API。审查时对照仓库内的组件源码，不对照模型的解释。
- 可访问性（焦点、标签、键盘）经常被漏掉，要有检查项，不能靠目视。
- 前端不能成为绕过工具网关的第二条写路径。高影响动作仍然调用后端已授权的接口。

## 2.4.3 后端

技巧：

- 先写失败测试或契约测试，再让模型实现，使错误行为有一个不会被辩解的判定。
- 外部调用显式写出超时、重试和幂等。重试只用于可证明安全的读或带幂等键的写。
- 错误分类要能被调用方区分：校验失败、无权限、下游超时、冲突。不要把它们收成一个“AI 出错了”。
- 配置和密钥从环境或密钥管理读入。审查生成代码时搜索密钥、令牌和内网地址。

注意点：

- 幻觉出来的库、参数和已废弃的 API 很常见。依赖必须在锁文件里，并且能在 CI 安装。
- 模型倾向于捕获所有异常并返回空成功。这种差异要在审查里拒绝。
- 为了“先跑通”生成的管理员接口，如果没有身份和审计，不能合并。

## 2.4.4 Agent、Prompt 和知识管道

技巧：

- 工具描述包含输入 Schema、输出 Schema、副作用、超时和错误类型。自然语言只作补充。
- 结构化输出用 Schema 约束，失败时重试有上限，超限后把原样结果交给人，不无限循环。
- 模型路由按任务配置：起草、分类、工具调用可以是不同模型。换模型要重跑评测，不在生产悄悄切换。
- 知识更新和索引构建是一条数据管道：解析、切分、嵌入、写入、抽样检查引用。它和在线问答分开部署，避免在请求路径里做全量重建。
- 评测用例从 Clarity 的例子导入，在 CI 里对 Prompt 和检索配置做回归。

注意点：

- 工具一旦能写外部系统，提示注入的影响就不再限于一句坏回答。开发期用无副作用的假工具跑主路径，写工具只在通过策略网关后打开。
- 不要把检索到的文档直接当成系统指令。文档进入用户或工具结果通道，并在拼接时标明这是资料。
- Agent 框架的状态对象不要出现在业务服务的公共 API 里。

## 2.4.5 审查生成代码时看什么

| 检查 | 通过的样子 |
| --- | --- |
| 范围 | 差异只包含任务声明的文件 |
| 契约 | 实现和 OpenAPI、JSON Schema 或 MCP 描述一致 |
| 测试 | 新增行为有失败用例；现有测试通过 |
| 依赖 | 新依赖有许可证记录，锁文件已更新 |
| 秘密 | 差异和日志样例里没有密钥和客户数据 |
| 失败 | 超时、空结果、冲突都有明确行为 |
| 权限 | 新工具或新接口有身份和资源范围 |

审查意见写在变更上。不接受“模型说这样更优雅”作为合并理由。

## 2.4.6 工具如何接入

Coding Agent 接在开发者环境或 CI 的隔离作业里，两种接入不要混用权限。

| 接入位置 | 允许 | 禁止 |
| --- | --- | --- |
| 本地 IDE 或 CLI | 读任务相关文件，改工作区，跑项目已有的测试命令 | 使用生产密钥；对默认分支强制推送 |
| CI 中的 Agent 作业 | 在分支上提出变更，跑门禁 | 合并自己的变更；读取生产数据库 |
| 运行时 Agent | 调用已登记工具 | 修改本服务的源代码或直接执行任意 shell |

规则文件（仓库中的 `AGENTS.md` 或工具自己的规则文件）只写仓库惯例和禁止事项，不写密钥，不替代规格。Spec Kit 一类的流程如果使用，命令在 Agent 对话中逐步执行，每步由人看过再进入下一步，见 2.1 节。

同类 Coding Agent 的对照见 [tools.md](../reference/tools.md) 第 9 节。密钥扫描产品的页面这一轮没有打开，开发阶段仍按本章已经写明的扫描要求执行。

## 2.4.7 退出条件

- 变更通过项目门禁和人工审查。
- 新的工具或 Prompt 有对应评测例子。
- 没有未评审的迁移和权限变更。
- 资产清单里新增的 Prompt、模型和索引配置已经登记版本。
